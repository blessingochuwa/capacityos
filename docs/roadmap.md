# Roadmap

This is the single place to see what CapacityOS has built and what's genuinely still open. **Completed phases** (0–27) are drawn directly from CLAUDE.md §39 and their ADRs — that section is the authoritative build order and this table should never drift from it. **Proposed future phases** are compiled from every deferral CLAUDE.md and the ADRs already named explicitly (§22 external integrations, §23 Chrome extension, and the "Deferred items" paragraph at the end of CLAUDE.md §39) — nothing below was invented for this document. Their numbering and grouping are a proposal, not a commitment: this project's own history (see Phase 13's ADR) is that "what phase comes next" gets decided deliberately, by asking, not by assuming a pre-written list — treat anything below "Completed phases" as provisional until CLAUDE.md §39 itself is amended to confirm it, the same way Phases 9–20 were each confirmed as they happened.

## Proposed future phases

None of these have a confirmed number, order, or ADR yet — each should be confirmed (with the user, per this project's established practice) before work starts, exactly as Phases 13–27 each were.

### 🔜 Proposed next: the rest of Prioritization

Phases 17-27 together shipped a deliberately reduced slice of the original Phase 17 PRD (each confirmed with the user before implementation, per CLAUDE.md §31's "smallest complete slice"). Still named, scoped, not dropped:

- The remaining three Recharts visualizations the PRD's own §15 names (Capacity vs. Priority matrix, Risk vs. Value quadrant, dependency timeline). The Phase 25 audit found each carries real, unspecified cross-domain ambiguity — Capacity-vs-Priority (whose capacity, over what period, aggregated how — no specification exists), Risk-vs-Value (`Risk` is a project-scoped *set*, not a single value — which risk, or what aggregation rule, represents "the" project's risk, is unspecified), and the dependency timeline (still blocked — `ProjectDependency` has no date/duration data at all) — all three reconfirmed unchanged by the Phase 26 and Phase 27 audits.
- **Scenario snapshots** — a snapshot of a scenario's hypothetical (rather than baseline) ranking, within a `PortfolioSnapshot`'s conceptual reach but genuinely ambiguous: `Scenario` (unlike `PrioritizationFramework`) supports a real, non-soft delete, so what happens to a scenario snapshot when its scenario is deleted needs a product decision before this is buildable (audited and explicitly not selected for Phase 22, re-confirmed still open — directly against current code, not merely repeated — by the Phase 23, Phase 24, Phase 25, Phase 26, and Phase 27 audits — see ADR 0022's Context).
- A rank-over-time or toggleable score/rank variant of the Phase 24 trend chart — audited and explicitly not selected for Phase 24 (a rank trend risks conflating a project's own change with a sibling project entering/leaving the ranking, and a MoSCoW framework has no rank at all — see ADR 0024's Decision).

An AI explanation of a Phase 22 snapshot comparison is resolved as of Phase 23 — see [ADR 0023](adr/0023-ai-snapshot-comparison-explanation.md). A multi-snapshot score-over-time trend chart is resolved as of Phase 24 — see [ADR 0024](adr/0024-portfolio-snapshot-trend.md). The PRD's own WSJF breakdown visualization is resolved as of Phase 25 — see [ADR 0025](adr/0025-wsjf-breakdown-visualization.md). An AI interpretation of the Phase 20 scenario-vs-baseline comparison is resolved as of Phase 26 — see [ADR 0026](adr/0026-ai-scenario-priority-comparison-explanation.md). The PRD's own Priority-vs-Effort scatter is resolved as of Phase 27 — see [ADR 0027](adr/0027-priority-effort-scatter-visualization.md). See [ADR 0020](adr/0020-scenario-priority-comparison.md)'s, [ADR 0021](adr/0021-portfolio-snapshots.md)'s, [ADR 0022](adr/0022-portfolio-snapshot-comparison.md)'s, [ADR 0023](adr/0023-ai-snapshot-comparison-explanation.md)'s, [ADR 0024](adr/0024-portfolio-snapshot-trend.md)'s, [ADR 0025](adr/0025-wsjf-breakdown-visualization.md)'s, [ADR 0026](adr/0026-ai-scenario-priority-comparison-explanation.md)'s, and [ADR 0027](adr/0027-priority-effort-scatter-visualization.md)'s Consequences for the authoritative list.

### 📋 Proposed, unscheduled

- **Risk, Stakeholder & Prioritization Import/Export registration is resolved as of Phase 36** ([ADR 0036](adr/0036-import-export-risk-stakeholder-prioritization.md)) — `risk` (a new nullable `external_id` column), `stakeholder` (matched by its existing `(project_id, person_id)` unique constraint, no schema change), and `project_priority_score` (the human-entered scoring inputs; `PrioritizationFramework` itself deliberately excluded as a `PRIORITIZATION_MANAGE`-gated privilege-escalation risk) are all registered into the existing Phase 6 pipeline. **`ProjectDependency` (Phase 18) Import/Export registration is resolved as of Phase 37** ([ADR 0037](adr/0037-import-export-project-dependency.md)) — its existing `(from_project_id, to_project_id, dependency_type)` unique constraint already supplied a complete natural key, so 0 migrations were needed; `BLOCKS`-only cycle detection reuses the same `detects_cycle` function the direct API already calls, via a cross-row batch-simulation technique mirroring WorkingSchedule's overlap pre-check. **`PortfolioSnapshot` (Phase 21) was audited in the same phase and deliberately left unregistered on both import and export** — its own model docstring already settles import (immutable, append-only like `AuditEvent`, "deliberately NOT read back as an input to any live computation," and its `create()` takes only a `framework_id`, so there is no user-supplied content to import); export was evaluated independently but the existing `ImportEntityType`-shared-enum architecture offers no way to expose it without also exposing an unguarded import path, and building that guard would be new infrastructure outside the phase's scope. This is a deliberate, documented non-registration, not an unaudited gap.
- **Org-wide cross-project Risk and Stakeholder registers** — both entities are currently nested under one Project only; a register spanning every project in an organization was named but not built (ADR 0013/0014 Consequences).
- **Membership- / user- / organization-management UI** — the membership roster/role/status slice is **done** as of Phase 28 ([ADR 0028](adr/0028-membership-management-ui.md)), the `User`-account create/disable/re-enable slice as of Phase 29 ([ADR 0029](adr/0029-user-account-management-ui.md)), and organization **rename** as of Phase 30 ([ADR 0030](adr/0030-organization-settings-ui.md)) — all frontend-only. The backend deactivation lifecycle was made **safe and reversible** in Phase 31 ([ADR 0031](adr/0031-organization-deactivation-safety.md)) and its **frontend** shipped in Phase 32 ([ADR 0032](adr/0032-organization-deactivation-reactivation-ui.md), frontend-only) — a Deactivation section and an inactive-org recovery panel that surface the backend's 422/403/404 verbatim. Phase 33 ([ADR 0033](adr/0033-global-inactive-organization-awareness.md)) closed the two Phase-32 follow-ups: `OrganizationSummary.is_active` on `/auth/me`, a persistent shell `InactiveOrganizationBanner`, and switcher filtering of deactivated orgs. The organization lifecycle UX is now complete for the current backend surface. The **account-directory search/filter box** is done as of Phase 34 ([ADR 0034](adr/0034-account-directory-search-filter.md)) — `q`/`status` query params, filtered server-side, global scope preserved. The **`USER_WRITE` organization-scoping question** is resolved as of Phase 35 ([ADR 0035](adr/0035-user-write-global-scope.md)) — the user was asked directly (no default was assumed), and chose to keep `USER_WRITE` global, matching `USER_READ`'s already-explicit global scope (ADR 0012 Decision 8). No code changed; the decision is now documented rather than open.
- **External integrations foundation** (CLAUDE.md §22) — Slack, Jira, Linear, Asana, ClickUp, Google Calendar, via an isolated adapter layer (`External System → Integration Adapter → CapacityOS Internal Model → Domain Engine`) so vendor-specific logic never spreads into the domain layer. Deliberately not started in any phase through 17.
- **SSO / OAuth / external identity provider** — deferred since Phase 10 (session-cookie auth was chosen specifically because a self-hosted option was sufficient for that phase's scope).
- **Billing / subscription** — no concept exists anywhere in the schema or domain model (ADR 0012 Consequences).
- **Organization hierarchies / sub-organizations** — every organization is currently a flat, independent tenant (ADR 0012 Consequences).
- **Chrome extension** (CLAUDE.md §23) — explicitly deferred; when built, it must call the CapacityOS API rather than duplicate any business logic client-side.
- **PostgreSQL verification of the Phase 15 last-owner concurrency guard** — the atomic-guarded-`UPDATE` technique is expected to hold under PostgreSQL's isolation levels (it's portable SQL), but this was verified against SQLite's single-file writer serialization only; a real PostgreSQL deployment should confirm it before being relied on as a production guarantee (ADR 0015 Consequences).
- **Team→Project access-grant inheritance, Person-keyed instance scoping (WorkingSchedule/AvailabilityException/PersonSkill), Scenario instance scoping** — audited and *deliberately retained* as role-only by Phase 16 (ADR 0016), not merely unbuilt. Re-opening any of these requires a new, explicit product requirement naming the missing ownership concept CLAUDE.md would need to define first — not a default next step.
