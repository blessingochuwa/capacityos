# ADR 0003: Phase 2 capacity engine decisions

- **Status:** Accepted
- **Date:** 2026-08-11

## Context

Phase 1 ([ADR 0002](0002-phase-1-domain-foundation.md)) built Person, Team, Project, Allocation, WorkingSchedule/WorkingScheduleEntry, and AvailabilityException, and deliberately stored no derived capacity number anywhere. Phase 2 turns those source facts into an explainable, deterministic capacity result (CLAUDE.md §10, §39). The formulas themselves (gross/unavailable/effective/allocated/remaining/utilization/over-allocation) are prescribed by CLAUDE.md §8 and the task spec; what this ADR records is the handful of genuinely ambiguous decisions needed to make those formulas concrete against the actual Phase 1 schema, plus one narrow, justified amendment to Phase 1 write-time validation.

## Decisions

**Allocation time-phasing: spread evenly across every calendar day in `[start_date, end_date]`, including non-working days.** `Allocation.allocation_hours` is a total over the period (ADR 0002, `app/models/allocation.py`), not a daily or weekly rate, so the engine must decide how to turn that total into a daily number. The chosen rule: `daily_hours = allocation_hours / (end_date - start_date + 1)`, applied uniformly regardless of the person's schedule. This is deliberately *not* schedule-aware (it does not skip weekends or non-working days) — the engine needs to be able to detect "allocation exists on a day the person doesn't normally work" as a real conflict (surfaced as over-allocation) rather than silently smoothing it away, and coupling the allocation math to a specific schedule would make that impossible. Multiple overlapping allocations for the same person (different projects) sum on a given day — this is the intended cross-project contention case, not an error. Implemented in `app/domain/capacity.py::allocation_amount_for_date`, rounded to 2 decimal places (see "Precision" below).

**Overlapping AvailabilityExceptions: allowed, resolved by "most restrictive wins."** For a given date, every exception covering it contributes an "available that day" value (0 if `hours is None`, else `hours`); effective capacity for that date is `min(scheduled_hours, *those values)` — never higher than the normal schedule, and never a naive sum (adding two exceptions' available-hours together would imply *more* availability than either alone, which has no real-world meaning). Overlap is allowed rather than rejected at write time because it's a legitimate scenario: a public holiday can legitimately fall inside a person's booked annual leave, and both are real, independently-recorded exceptions. Implemented in `_effective_capacity_for_date`.

**Overlapping WorkingSchedules for the same person: rejected at write time (Phase 1 amendment).** Unlike availability exceptions, two simultaneously-effective *normal* recurring schedules for one person isn't a realistic scenario — a person has one baseline working pattern at a time — so an overlap here is a data-entry mistake, not a legitimate case to resolve arithmetically. `WorkingScheduleService.create`/`.update` (`app/services/working_schedule.py`) now reject (`DomainValidationError` → 422) a schedule whose effective date range overlaps another schedule already recorded for the same person. This is an app-layer check only — no schema or migration change — and does not affect any Phase 1 behavior other than making an already-nonsensical write fail loudly instead of silently succeeding. The capacity engine's schedule-selection function (`_scheduled_hours_for_date`) still contains a defensive most-recently-created tie-break for the case where more than one schedule matches a date, documented in its docstring as unreachable via the API and intended only for data written before this validation existed.

**Zero effective capacity → `utilization = None`, never `0`.** Both "0 effective / 0 allocated" (e.g. a person on full leave with nothing assigned) and "0 effective / >0 allocated" (a genuine conflict: work assigned to someone with no capacity) return `utilization: null`. `0%` would misleadingly read as "available but unused"; `null` says "there is nothing to divide by." The conflict in the second case is still fully visible via `over_allocation` (positive) and `remaining_capacity` (negative) — nothing is hidden by returning `null`.

**Canonical week: Monday–Sunday**, defined once in `app/domain/dates.py` (`WEEK_START_WEEKDAY = 0`, matching `WorkingScheduleEntry.weekday`'s existing `date.weekday()` convention) rather than assumed ad hoc anywhere else. The capacity API itself does not have a separate "period type" — `start_date`/`end_date` are always explicit query parameters, and day/week/arbitrary-range are all the same underlying calculation (`calculate_period_capacity`) with different bounds. `week_range()` exists as a reusable helper for a future caller that needs "the week containing this date," but Phase 2 doesn't require it internally.

**Team utilization is weighted, not averaged**, and team-level `remaining_capacity`/`over_allocation` are computed from team totals with the same formula used at the person level — not by summing each member's own `over_allocation`. `sum(allocated) / sum(effective)` correctly reflects a team's aggregate position; averaging member percentages would treat a person with 2 effective hours and a person with 40 as equally significant to the team number, which misrepresents reality. Deriving team `over_allocation` from totals (rather than summing member `over_allocation`) means one member's overload can be offset by another's slack in the *team* number — this is intentional (it's what "team-level slack" means) and never hides the individual case, because the team API response (`TeamCapacityRead.members`) always includes every member's own full result alongside the aggregate.

**A pragmatic ~3-year date-range guard** (`MAX_RANGE_DAYS = 1096` in `app/services/capacity.py`) rejects absurdly large ranges with a 422. This exists purely to bound the size of `daily_breakdown` against an obvious client mistake (e.g. a swapped year) — it is not a statement about how far ahead CapacityOS thinks organizations should plan.

**Precision: hour quantities are rounded to 2 decimal places, utilization to 4.** This matches the `Numeric(4,2)`/`Numeric(6,2)` precision Phase 1 already uses for `WorkingScheduleEntry.hours`, `AvailabilityException.hours`, and `Allocation.allocation_hours` — it is not an arbitrary choice. The only place division happens is time-phasing an allocation across days (`allocation_amount_for_date`); that per-day amount is rounded once, and every period/team total is a straight sum of already-rounded daily figures, so the daily breakdown and the totals can never disagree with each other. One consequence: when a total doesn't divide evenly across days (e.g. 20 hours over 3 days = 6.67/6.67/6.66), the summed total may differ from the raw `allocation_hours` by at most one cent — an explainable, bounded rounding artifact, not a defect.

## Consequences

- Creating or updating a `WorkingSchedule` whose effective range overlaps an existing one for the same person now returns 422 instead of succeeding — a behavior change from Phase 1, though no Phase 1 test exercised that case (each existing test uses a single schedule per person).
- The capacity engine (`app/domain/capacity.py`) has no SQLAlchemy or FastAPI imports and is tested entirely without a database (`apps/api/tests/domain/`), per CLAUDE.md §10.
- `AllocationUnit.TOTAL_HOURS` remains the only allocation unit; a future `hours_per_week`/`hours_per_day` unit would need its own time-phasing rule in `allocation_amount_for_date`, not a change to this one.
- No Alembic migration was needed for Phase 2 — every decision above is either pure calculation or app-layer validation, not a schema change.
