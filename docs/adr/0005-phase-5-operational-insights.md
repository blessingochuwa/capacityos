# ADR 0005: Phase 5 operational insights decisions

- **Status:** Accepted
- **Date:** 2026-08-14

## Context

Phases 1–4 gave CapacityOS trustworthy source data, a deterministic capacity engine (`app/domain/capacity.py`), read-only planning views, and scenario/what-if planning (`app/domain/scenario.py`). None of it answers "where should I look?" — an operator still has to manually scan capacity/scenario views to find the one team member, project, or scenario risk that actually needs attention.

Phase 5 adds that layer: a read-only, deterministic decision-support system that classifies existing capacity/scenario facts into explainable, prioritized **signals**. The task spec's own principle is the binding constraint: the objective is "where should I look," not "what should I do" — recommendations stay conservative, and every number is either a fact already produced by the Phase 2/4 engines or a deterministic, existence-gated derivation of one. No AI, no integrations, no new capacity formula.

**Phase renumbering.** This work was originally going to be scoped as a later phase (CLAUDE.md §39 previously listed Import/Export at Phase 5, Skills/Bottleneck analysis at Phase 6, AI insight layer at Phase 7). It is instead pulled forward and becomes the official Phase 5, pushing Import/Export to Phase 6, Skills/Bottleneck to Phase 7, and the AI insight layer to Phase 8. Rationale: insights sit directly on top of the Phase 2 capacity engine and Phase 4 scenario engine with no new subsystem dependencies (no new entities, no new persistence beyond one config value), while import/export and skills/bottleneck each introduce their own new domain concepts and are better sequenced after this layer exists to consume them later. Confirmed with the product owner before implementation.

## Decisions

**One new backend-owned threshold: LOW_CAPACITY, expressed as hours-per-day.** ADR 0004 deliberately kept "at capacity" judgment calls frontend-only (`features/capacity/constants/thresholds.ts::AT_CAPACITY_MIN`) to avoid two thresholds drifting apart. Phase 5 reverses that stance for exactly one signal: `Settings.low_capacity_threshold_hours_per_day` (`app/core/config.py`, default `1.00`), consumed by `app/domain/insights.py::classify_capacity_signal`. This is deliberate and scoped, not a blanket reversal — `AT_CAPACITY_MIN` remains frontend-only and untouched, and it is the *only* new threshold this phase introduces. Justification: LOW_CAPACITY drives an org-visible API signal that any future client (not just this one frontend's presentation layer) can consume — keeping it frontend-only would either force every future consumer to reinvent the same judgment call or fragment it across clients. Expressed as hours-per-day (not a flat period-total) so it means the same thing whether the queried range is one day or `MAX_RANGE_DAYS` (~3 years) long: "less than this many hours of slack per working day, on average, across the period" — compared against `remaining_capacity / period_days`, never against `remaining_capacity` directly.

**No other invented thresholds — concentration and imbalance are unconditional structural facts.** `calculate_concentration`'s `top_n=2` is a *reporting window* ("what do the top 2 contributors hold"), not a pass/fail cutoff on whether 2 is too many; it fires whenever there are more than `top_n` contributors and total hours are positive — an existence gate. `calculate_imbalance` fires whenever at least 2 team members have non-null utilization and the spread is `> 0` — again an existence gate ("there is literally a difference"), never a magnitude judgment about whether the difference is "meaningful." Neither escalates beyond `info` severity. A future phase could add a second configurable threshold to either if product feedback shows they need to surface as warnings, but that is out of this phase's locked scope — only one new threshold was approved.

**Signal classification reuses `ScenarioCalculationService._risks`' exact mutual-exclusivity style, extended by one tier.** `classify_capacity_signal` (`app/domain/insights.py`) is the same `if`/`elif` chain Phase 4's risk detection already uses (over-allocation, then exactly-zero-remaining-capacity gated on positive effective capacity), with LOW_CAPACITY added as a third, weakest tier. An entity never carries more than one of `over_allocation`/`zero_remaining_capacity`/`low_capacity` for the same period.

**Project capacity pressure reuses `aggregate_team_capacity` verbatim, over the ad-hoc set of people allocated to the project.** The same "any `Sequence[PersonCapacityResult]` is a team" seam ADR 0004 already exploited for scenario aggregates. `InsightService._pressure_signal` batch-loads the project's assigned people's own planning facts (`load_people_facts`), runs each through the unmodified `calculate_period_capacity`, and aggregates — no new formula. This means the signal reflects those people's *overall* capacity picture (every commitment, not just this one project), the same way a real team's over-allocation would be judged. The project's own demand (`ProjectDemandResult.allocated_hours`, from `CapacityService.get_project_demand`) is reported alongside as context, not blended into the aggregate formula.

**Every Insights endpoint is scope-required — no org-wide scan.** `/api/v1/insights/{people,teams,projects}/{id}/signals`, `/api/v1/insights/scenarios/{id}/signals`, and `/api/v1/insights/teams/{id}/summary` all require an explicit id, exactly like every existing capacity/scenario endpoint (CLAUDE.md §26/§27: bounded by request scope, not total system size). `BaseRepository.list()` (unordered, unfiltered) remains the only "list everything" primitive in the codebase; Phase 5 does not add a bulk "list all teams needing attention" endpoint.

**Severity-first priority order, refining the brief's flat example ordering.** `InsightService._prioritize` sorts by `(severity, is_new-first, type-family, entity_label, entity_id)`. The brief's own literal example list ("critical over-allocation, new scenario risks, existing warnings, concentration, imbalance, informational") would let a merely-informational new scenario signal outrank an existing critical over-allocation — incoherent, since severity is the one objective "how bad" fact every signal category shares. `is_new` and signal-type family are tiebreakers within a severity tier only, not top-level sort keys.

**Scenario signals wrap, never duplicate, `ScenarioCalculationService`'s own risk/comparison output.** `InsightService.get_scenario_signals` calls `ScenarioCalculationService.comparison(...)` and reclassifies each `RiskRead` into a `SignalRead` (severity via `scenario_risk_severity`, a `trend` via `scenario_risk_trend` for existing risks) — it never re-detects over-allocation or zero-remaining-capacity itself. `tests/api/test_insights.py::test_get_scenario_signals_reuses_comparison_risk_detection` asserts the signal list and `/scenarios/{id}/comparison`'s risk list agree exactly, proving there is exactly one risk-detection code path.

**`SignalRead` is one flat Pydantic model, not a discriminated union.** Unlike `ScenarioOperationPayload` (a union because payloads are *executed* by type-specific code — `apply_scenario_operations` dispatches per `operation_type`), signals are only ever *displayed* in a uniform list. A union would force the frontend to type-narrow 8 ways just to render a row, for no behavioral benefit. Fields beyond the common core (`type`, `severity`, `entity_*`, `start_date`/`end_date`, `explanation`) are nullable and populated only for the signal types documented on each field.

**Every signal carries a fully-formed `explanation` string, built server-side.** The frontend renders it verbatim and never reconstructs a sentence from the numeric fields — the same "backend explains, frontend displays" discipline `RiskList`/`ImpactSummary` already follow for Phase 4.

## Consequences

- No changes to Phase 1–4 behavior; the full existing suite (195 backend tests before this phase, 64 frontend tests before this phase) passes unchanged after Phase 5 (224 backend / 78 frontend after).
- New `Settings.low_capacity_threshold_hours_per_day` field — changing it changes LOW_CAPACITY classification org-wide with no code change, but requires an app restart (`get_settings()` is `@lru_cache`'d), the same operational characteristic as every other `Settings` field.
- No Alembic migration: Phase 5 adds no tables or columns, only pure/service/API code and one `Settings` field.
- Known limitation: `project_capacity_pressure` issues a second batch fact-load beyond `get_project_demand`'s own (schedule/availability/allocation facts for the project's assigned people) — bounded by the project's own assigned-people count, not a performance concern at current scale (CLAUDE.md §26), but worth knowing this endpoint is not "free" relative to `GET /capacity/projects/{id}`.
- Known limitation: concentration risk and capacity imbalance are capped at `info` severity by design; a future phase could add a second configurable threshold for either if product feedback shows they need to surface more urgently, but that is explicitly out of this phase's locked scope.
- Operational insights has no AI, no integrations, no auth, no skills/bottleneck logic — strictly signal classification + explanation + prioritization on top of Phase 2/4, per the phase's own boundary.
