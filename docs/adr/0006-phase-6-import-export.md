# ADR 0006: Phase 6 import/export decisions

- **Status:** Accepted
- **Date:** 2026-08-14

## Context

Phases 1–5 gave CapacityOS trustworthy source data, a deterministic capacity engine, scenario/what-if planning, and operational insights — but every one of those facts still has to be entered by hand, one record at a time, through the UI or a raw API call. That's impractical for real operational use: a team onboarding CapacityOS with 50 people, a dozen projects, and a quarter of allocations already sitting in a spreadsheet has no way to get that data in without hundreds of manual form submissions, and no way to get current data back out for backup, inspection, or reuse elsewhere.

Phase 6 adds that data-portability layer: CSV/JSON import and export for the core operational entities. It is explicitly *not* the integrations phase (CLAUDE.md §22/§32) — no Slack, Jira, Linear, calendars, or OAuth here. The task spec's own architectural principle is the binding constraint, same as every phase since Phase 2: import must not become a second capacity engine or a second set of business rules. An imported row is only ever a proposed `PersonCreate`/`AllocationUpdate`/etc. payload, validated and written through the exact same `app/services/*.py` classes every other write path already uses.

## Decisions

**Two-stage validate/apply, stateless — no persisted import-job entity.** `ImportService.validate` and `ImportService.apply` (`app/services/import_service.py`) both run the identical parse → normalize pipeline on demand; `apply` additionally writes. There is no `ImportBatch`/`ImportJob` table tracking in-flight imports across requests — the client re-uploads the same file it already validated to apply it (`POST /api/v1/imports/{entity_type}/apply`, same body shape as `/validate`). This was a deliberate simplification: a persisted job entity would need its own lifecycle, storage of the original file or parsed rows between requests, and expiry policy, for a workflow that completes in a single round trip at the file sizes this phase targets (`Settings.import_max_file_size_bytes` = 5 MiB, `Settings.import_max_rows` = 5000). **Known limitation:** there is consequently no server-side history of past imports — see Consequences.

**Atomicity comes entirely from the existing single-commit-per-request contract — no new transaction code.** `ImportService` never calls `session.commit()`/`rollback()` itself. `apply()` only begins calling `create()`/`update()`/`add_member()` once every row in the batch has already been confirmed clean by a read-only pre-check pass (`_prepare`); if a row is invalid, `apply()` returns `applied=False` without writing anything. `app/core/database.py::get_db`'s existing `except Exception: db.rollback()` still discards everything flushed so far in the same request if a service call raises mid-write (a narrow concurrent-write race the pre-check couldn't predict) — the identical mechanism every other multi-step service call in this codebase already relies on, not something Phase 6 invented.

**Identity strategy is per-entity, chosen from what's already a real unique constraint — plus one new column where none existed.** Person matches by `email` (already `UNIQUE`); Team matches by `name` (already `UNIQUE`); TeamMembership matches by the resolved `(person_id, team_id)` pair (already the table's own uniqueness rule) and is create-or-noop only — it has no mutable fields, so there is no "update" case, only `create`/`unchanged`. Project, Allocation, WorkingSchedule, and AvailabilityException have no natural key (a project name is not unique; an allocation has no business identifier at all), so this phase adds a nullable, unique `external_id: str | None` column to all four (migration `3518aa2c92c3_phase_6_import_export`). A row without an `external_id` for one of these four entity types has no identity at all and always creates — reimporting the same file without external ids produces duplicates, by design, since there is nothing to match against; this is documented per-field in `app/schemas/*.py` and covered by `test_project_import_without_external_id_always_creates_on_reimport`. **Never name-matched as a fallback identity** for any of the four, since none of their names/labels are unique — silently matching on a non-unique field would risk merging two unrelated records.

**Reference resolution is literal-id-or-natural-key → `INVALID_REFERENCE`, never a soft skip.** A row's `person_id`/`person_email`, `project_id`/`project_external_id`, or `team_id`/`team_name` is resolved against a lookup batch-loaded once per file (never per row — CLAUDE.md §27), and an unresolvable reference is always a blocking row error, never a silently-skipped row or a null foreign key. `app/domain/import_export_diff.py::resolve_person_reference`/`resolve_project_reference`/`resolve_team_reference` are the only three functions that do this, shared by every entity that references another.

**Dependency ordering is per-entity-type sequential imports, not automatic multi-entity resolution.** Each `/validate`/`/apply` call imports exactly one `ImportEntityType` at a time; a file mixing people and allocations isn't a supported shape. The user is expected to import in dependency order — People → Teams → TeamMemberships → Projects → WorkingSchedules/AvailabilityExceptions/Allocations — matching CLAUDE.md §39's own suggested order. An Allocation row referencing a Project that hasn't been imported yet doesn't get silently deferred or retried; it fails validation immediately with `INVALID_REFERENCE`, telling the user exactly what's missing rather than guessing at an ordering. This was chosen over an "automatically topologically sort a mixed file" design because it keeps the format simple (`ENTITY_COLUMNS` stays one flat header set per entity, not a discriminated multi-entity envelope) and keeps failures immediately actionable instead of surfacing as a second-pass batch failure.

**Import modes: `upsert` (default), `create_only`, `update_only` — never a destructive sync.** `apply_mode_policy` (`app/domain/import_export_diff.py`) reclassifies an already-normalized row after the fact: `create_only` turns a would-be update into a blocking `CONFLICT`; `update_only` turns a would-be create into a blocking `NO_MATCH_FOR_UPDATE_ONLY`. There is deliberately no "replace" or "sync" mode that deletes anything not present in the uploaded file — CLAUDE.md's own instruction and the task spec agree this is dangerous as a default and, if ever added, must be a separate, strongly-confirmed future feature.

**Upsert "unchanged" is a real field-level diff, not "record already exists."** `_unchanged` (`app/domain/import_export_diff.py`) compares only the fields the row actually supplied (`model_dump(..., exclude_unset=True)`) against the current stored value, via the same JSON-mode serialization `operation_payload_to_dict` already uses for scenario payloads (so `Decimal("8")` vs `Decimal("8.00")` never registers as a false change). A blank cell means "leave this field alone," exactly like every existing `XxxService.update()`'s `exclude_unset=True` semantics — never "clear it to `None`," which would raise an `IntegrityError` on a NOT NULL column like `Project.status`. This is what makes repeated identical imports deterministically report `unchanged`, not `updated`.

**`ENTITY_COLUMNS` is the single source of truth for column shape, shared verbatim by import parsing, export writing, and template generation.** `app/domain/import_export_parsing.py::ENTITY_COLUMNS` defines each entity's header/column order once; `parse_csv_rows`/`parse_json_rows` use it to check required headers, `ExportService._serialize` uses it for CSV column order, and `build_template` uses it for both the template's headers and its CSV `DictWriter` fieldnames. Three code paths reading from one definition, so they cannot drift out of sync with each other.

**Templates are pure and DB-free.** `build_template(entity_type, fmt)` needs no repository — it emits `ENTITY_COLUMNS`' headers plus one hand-written, schema-valid example row (`_TEMPLATE_EXAMPLES`) per entity, exposed as `GET /api/v1/imports/{entity_type}/template?format=csv|json`. Unlike `/validate`/`/apply`/`/exports/*`, this endpoint touches no repository or service at all — it is static reference output, the same shape a real export would have, that the frontend can link to before any file exists.

**CSV formula-injection defense (OWASP) on export, not on import.** `sanitize_csv_cell` prefixes a leading apostrophe onto any cell whose first character (`=`, `+`, `-`, `@`) a spreadsheet application would interpret as a formula, applied to every cell `ExportService` writes. Import never needs the equivalent — an imported value is parsed and validated by the target Pydantic schema (e.g. `allocation_hours` must be a non-negative `Decimal`), so a formula-injection string is simply rejected as the wrong type, not re-emitted into a file another user might open.

**Working schedule overlap is pre-checked across the whole batch before any row writes, mirroring `WorkingScheduleService`'s own existing overlap rule exactly.** `ImportService._prepare_working_schedule` seeds every referenced person's complete existing schedule set (`list_all_for_people`, not date-bounded), then `_check_working_schedule_overlap` simulates the batch in file order — so row 2 sees the effect of row 1's create — using the same `ranges_overlap` domain function `WorkingScheduleService` calls at write time. This is Level 3 (domain) validation, run once during the read-only pre-check pass, not a second overlap rule invented for import.

**Synchronous processing is correct at this phase's scale — no job queue.** `import_max_rows` (5000) and `import_max_file_size_bytes` (5 MiB) bound worst-case request time to well under typical HTTP timeouts. `ImportService`/`ExportService` take repositories and settings as constructor arguments with no framework coupling, so a future asynchronous/background version (Celery, an internal queue, whatever CapacityOS eventually adopts) could wrap the same `validate`/`apply` methods without a rewrite — but adding that infrastructure now, before there's a demonstrated need, would violate CLAUDE.md §21/§25's dependency discipline.

## Consequences

- No changes to Phase 1–5 behavior; the full existing test suite passes unchanged alongside the new Phase 6 tests.
- New `external_id` column (nullable, unique) on `projects`, `allocations`, `working_schedules`, `availability_exceptions` — one Alembic migration (`3518aa2c92c3_phase_6_import_export`). `alembic check` reports the same SQLite CHECK-constraint text-diff false positive against the five untouched enum columns that ADR 0002/0004/0005 already document — confirmed by it firing identically for constraints this migration never touches, not something Phase 6 introduced.
- Three new `Settings` fields (`import_max_file_size_bytes`, `import_max_rows`, `export_max_rows`) — changing any of them changes the corresponding limit org-wide with no code change, subject to the same `@lru_cache`-requires-restart characteristic every other `Settings` field already has.
- **Known limitation, deferred by design:** no persistent import history/audit trail. An apply's result (created/updated/unchanged/invalid counts, per-row detail) is returned in that request's response only — there is no `GET /api/v1/imports/history` and no stored record of who imported what, when. CapacityOS has no auth yet (CLAUDE.md §32) to attribute an import to a user in the first place; a future audit-trail phase should add both together rather than half-tracking imports without an actor.
- **Known limitation, deferred by design:** no destructive sync/replace import mode. Only `upsert`/`create_only`/`update_only` exist; "delete anything not in this file" is explicitly out of scope per CLAUDE.md and the task spec, and would need its own strongly-confirmed design if ever added.
- **Future integration seam:** a later integrations phase (Jira, Linear, an HRIS, etc.) can reuse this exact validate/apply pipeline unmodified by writing an adapter that maps the external system's records into the same normalized row shape `ENTITY_COLUMNS` already defines, rather than inventing a parallel write path per integration.
- Import/export has no AI, no external integrations, no auth, no skills/bottleneck logic, and calculates nothing — strictly parse, validate, and write through the existing domain services, per the phase's own boundary.
