# Architecture Overview

This is a summary for orientation. [CLAUDE.md](../CLAUDE.md) is the governing source of truth — if anything here conflicts with it, CLAUDE.md wins.

## System boundary

```text
apps/web (React + TypeScript + Vite)
      │  HTTP (fetch, versioned REST)
      ▼
apps/api (FastAPI)
      │  api/          — thin HTTP routes: validation, serialization, DI
      │  services/      — orchestration
      │  domain/         — pure, deterministic business rules (the capacity engine)
      │  repositories/    — persistence access
      ▼
Database (SQLite in dev, PostgreSQL-compatible; SQLAlchemy + Alembic)
```

`packages/contracts` holds TypeScript types shared between `apps/web` and `apps/api`'s contracts, populated once there is real domain data to share.

## Non-negotiable rules (see CLAUDE.md for full detail)

- **Deterministic core** (CLAUDE.md §4): all capacity math (working hours, availability, realistic capacity, allocation, utilization, over/under-allocation, skill bottlenecks) lives in `apps/api/app/domain` as pure, independently-testable functions. AI is never the source of truth for these numbers.
- **Thin API routes** (CLAUDE.md §6): `apps/api/app/api` handles HTTP concerns only; business logic belongs in `services`/`domain`.
- **No business logic in React components** (CLAUDE.md §6): complex calculations stay server-side; the frontend consumes and presents.
- **Postgres-compatible from day one** (CLAUDE.md §7): SQLite is a dev convenience; no SQLite-specific assumptions in domain/persistence code.
- **Phased build order** (CLAUDE.md §39): don't implement a phase before the one before it is stable.

## Current state (Phase 14)

The domain foundation (Phase 1) exists: Person, Team/TeamMembership, Project, Allocation, WorkingSchedule/WorkingScheduleEntry, and AvailabilityException — with SQLAlchemy models, an Alembic migration, Pydantic contracts, repositories, services, and thin CRUD routes under `/api/v1/`. See [docs/domain-concepts.md](./domain-concepts.md) for what each entity means (in particular, the WORKING SCHEDULE ≠ AVAILABILITY ≠ ALLOCATION ≠ CAPACITY distinction) and [docs/adr/0002-phase-1-domain-foundation.md](./adr/0002-phase-1-domain-foundation.md) for the implementation decisions behind them.

Phase 2 adds the deterministic capacity engine: `app/domain/capacity.py` and `app/domain/dates.py` are pure, database-free calculations (tested without a database under `apps/api/tests/domain/`) that turn `WorkingSchedule + AvailabilityException + Allocation` into gross/effective/allocated/remaining capacity, utilization, and over-allocation — for a person, a team, or a project's demand — exposed through three read-only endpoints under `/api/v1/capacity/`. See the "Capacity Engine" section of [docs/domain-concepts.md](./domain-concepts.md#capacity-engine-phase-2) for the formulas and [docs/adr/0003-phase-2-capacity-engine.md](./adr/0003-phase-2-capacity-engine.md) for the design decisions (allocation time-phasing, overlapping-exception handling, zero-capacity utilization, weighted team utilization).

Phase 3 adds the read-only capacity dashboard (`apps/web/src/features/capacity/`): a team overview, per-person and per-project views, all consuming the Phase 2 endpoints verbatim — no capacity math in the frontend.

Phase 4 adds scenario planning (`app/domain/scenario.py`, `app/services/scenario*.py`, `apps/web/src/features/scenarios/`): hypothetical "what if?" exercises that never write to production data. A `Scenario` is a baseline period plus a list of typed operations (add/adjust/remove/move an allocation, shift a project's dates, change availability, add a hypothetical resource); calculating one builds a hypothetical version of the same facts Phase 2 already consumes and runs them through the **unmodified** Phase 2 engine, then compares the two results. See [docs/domain-concepts.md](./domain-concepts.md#scenario-planning-phase-4) for the concepts and [docs/adr/0004-phase-4-scenario-planning.md](./adr/0004-phase-4-scenario-planning.md) for the design decisions (why no engine refactor was needed, the operation type set, JSON+discriminated-union payload storage, no caching).

Phase 5 adds operational insights (`app/domain/insights.py`, `app/services/insight_service.py`, `apps/web/src/features/insights/`): a read-only decision-support layer that classifies existing Phase 2/4 facts into explainable, prioritized signals — over-allocation, zero-remaining-capacity, low-capacity, project concentration risk, team capacity imbalance, project capacity pressure, and scenario deltas — answering "where should I look?" rather than "what should I do?" No second capacity engine and no new capacity formula: signals are derived from the same `calculate_period_capacity`/`aggregate_team_capacity`/`calculate_project_demand` results Phase 2 already produces, plus `ScenarioCalculationService`'s existing risk detection for scenario deltas. See the "Operational Insights" section of [docs/domain-concepts.md](./domain-concepts.md#operational-insights-phase-5) for the concepts and [docs/adr/0005-phase-5-operational-insights.md](./adr/0005-phase-5-operational-insights.md) for the design decisions (the phase renumbering, the one LOW_CAPACITY threshold and why it reverses ADR 0004's frontend-only stance, severity/priority rules).

Phase 6 adds import/export (`app/domain/import_export_parsing.py`, `app/domain/import_export_diff.py`, `app/services/import_service.py`, `app/services/export_service.py`, `apps/web/src/features/import-export/`): CSV/JSON portability for the core operational entities (People, Teams, TeamMemberships, Projects, WorkingSchedules, AvailabilityExceptions, Allocations) — deliberately excluding Scenarios and Insights, which are derived/hypothetical rather than source data. Import is a two-stage validate-then-apply flow: nothing is written until the user explicitly confirms a validation report showing exactly what will be created, updated, left unchanged, or rejected. Imported rows flow through the same `PersonCreate`/`AllocationUpdate`/etc. schemas and `app/services/*.py` classes every other write path already uses — no second capacity engine, no import-specific business rules. See the "Import / Export" section of [docs/domain-concepts.md](./domain-concepts.md#import--export-phase-6) for the concepts and [docs/adr/0006-phase-6-import-export.md](./adr/0006-phase-6-import-export.md) for the design decisions (identity/upsert strategy, validation levels, atomicity, dependency ordering).

Phase 7 adds skills & bottleneck analysis (`app/domain/skills.py`, `app/services/skill*.py`, `apps/web/src/features/skills/`): a skill dimension — `Skill`, `PersonSkill`, `ProjectSkillRequirement` — layered on top of the unmodified Phase 2 engine to distinguish SKILL capacity from TOTAL capacity. Qualified-capacity, coverage, and concentration calculations reuse the same batched `load_people_facts`/`calculate_period_capacity` pipeline every prior phase uses; three new signal types (`skill_gap`, `single_skill_holder`, `skill_concentration`) plug into the **existing** Phase 5 insights framework rather than a second one, so the Insights page shows skill bottlenecks with no new route. Skill/PersonSkill/ProjectSkillRequirement are also registered into the existing Phase 6 import/export system. See the "Skills & Bottleneck Analysis" section of [docs/domain-concepts.md](./domain-concepts.md#skills--bottleneck-analysis-phase-7) for the concepts and [docs/adr/0007-phase-7-skills-bottleneck-analysis.md](./adr/0007-phase-7-skills-bottleneck-analysis.md) for the design decisions (qualification semantics, severity rules, why there's no `/bottlenecks/` API, the documented-but-not-built scenario integration seam).

Phase 8 adds an AI insight layer (`app/integrations/ai/`, `app/services/ai_context.py`, `app/services/ai_service.py`, `apps/web/src/features/ai/`): an optional, provider-abstracted interpretation layer sitting strictly above the existing Phase 2/5/7 engines — `FACTS → DETERMINISTIC ENGINE → SIGNALS → AI INTERPRETATION`, never the reverse. Typed `AIInsightContext` objects (never a serialized SQLAlchemy model) are built from the same `CapacityService`/`InsightService`/`ScenarioCalculationService`/`SkillCapacityService` outputs every prior phase already produces; a swappable `AIProvider` (`AnthropicAIProvider` in production, `MockAIProvider` for the entire test suite and provider-free local development) returns Pydantic-validated structured output, which is grounded against an allow-list of the facts actually sent before any `source_reference` reaches the client. With no provider configured, every deterministic feature — capacity, insights, scenarios, skills, import/export — works identically; AI endpoints return a clear "unavailable" state instead of erroring. See the "AI Insight Layer" section of [docs/domain-concepts.md](./domain-concepts.md#ai-insight-layer-phase-8) for the concepts and [docs/adr/0008-phase-8-ai-insight-layer.md](./adr/0008-phase-8-ai-insight-layer.md) for the design decisions (provider abstraction, grounding enforcement, prompt-injection defense, the envelope response pattern, why `ask` doesn't use dynamic tool-calling).

Phase 9 adds production readiness, governance & observability (`app/core/logging.py`, `app/api/middleware.py`, `app/core/exceptions.py`'s two new handlers, `app/api/v1/health.py`'s readiness route): structured JSON logging with per-request correlation IDs, a liveness/readiness split (readiness checks database connectivity only — AI availability never affects it), an explicit `validate_production_config` startup gate that refuses to run `ENVIRONMENT=production` on a development default (SQLite, the mock AI provider, or an open CORS policy), two new exception handlers (database-unavailable → 503, catch-all → 500) that extend rather than replace FastAPI's existing error conventions, request/field size limits, and a fixed `astral-sh/setup-uv` CI failure. No new feature, no new domain concept, no new database table. See [docs/production-readiness.md](./production-readiness.md) for the operational reference (local dev, running checks, health/readiness, logging, troubleshooting, the full readiness checklist) and [docs/adr/0009-phase-9-production-readiness.md](./adr/0009-phase-9-production-readiness.md) for the design decisions.

Phase 10 adds identity, authentication, RBAC & audit (`app/models/{user,session,audit_event}.py`, `app/domain/authorization.py`, `app/core/security.py`, `app/api/deps.py`, `app/api/v1/{auth,users,audit}.py`): httpOnly-cookie session authentication (opaque, hash-compared tokens — no JWT, no `SESSION_SECRET_KEY`), a five-role RBAC model (`Owner`/`Admin`/`Manager`/`Member`/`Viewer`) enforced through one centralized `has_permission`/`require_permission` seam rather than scattered role checks, and a persistent, append-only `AuditEvent` trail for every mutation, login event, and permission denial. `User` is a new, deliberately separate identity concept from `Person` — nullable one-to-one, not a merge. Every existing route gained an authentication/permission dependency; no existing service method's signature changed, and the deterministic engine, scenarios, insights, skills, import/export, and AI layers are byte-for-byte unchanged (the full pre-Phase-10 test suite passes unmodified). See [docs/adr/0010-authentication-rbac-audit.md](./adr/0010-authentication-rbac-audit.md) for the design decisions, including two real concurrency/session-lifecycle bugs caught only by testing against a live server rather than the in-memory test suite.

Phase 11 adds instance-level resource authorization (`app/models/{team_access_grant,project_access_grant}.py`, `app/services/access_grant.py`, `app/api/v1/access_grants.py`): Phase 10's `has_permission`'s unused `resource` parameter becomes real via a `ResourceScope` the caller resolves before calling it (the pure domain function itself stays database-free). A `Manager`'s write/delete authority on a specific `Team` or `Project` now requires an explicit `TeamAccessGrant`/`ProjectAccessGrant` row — `Owner`/`Admin` remain unconditionally authorized (role-based, not grant-based), and reads stay global for every role, including Manager. Two new FastAPI dependency factories (`require_team_access`/`require_project_access`) are drop-in replacements for `require_permission` on path-resolved routes (Team, TeamMembership, Project, ProjectSkillRequirement); Allocation's project scope is resolved inline from the request body (create) or the existing row (update/delete), since `AllocationUpdate` has no `project_id` field to smuggle a re-point through. Grant/revoke management (`/api/v1/{teams,projects}/{id}/access-grants`) is gated on a new `Permission.ACCESS_MANAGE`, held only by Owner/Admin — making Manager self-escalation structurally impossible, not merely runtime-checked. `Person`/`WorkingSchedule`/`AvailabilityException`/`PersonSkill`/`Skill`/`Scenario` remain deliberately unscoped this phase (no single unambiguous Team/Project parent to key scope on without inventing a derived-authorization chain). See [docs/adr/0011-instance-level-resource-authorization.md](./adr/0011-instance-level-resource-authorization.md) for the design decisions, including a concurrency test suite run against a real file-backed SQLite database rather than the in-memory test fixture.

Phase 12 adds organizations & multi-tenancy (`app/models/{organization,organization_membership}.py`, `app/services/{organization,organization_membership}.py`, `app/api/v1/organizations.py`): every organization-owned entity — Person, Team, TeamMembership, Project, Allocation, WorkingSchedule, AvailabilityException, Skill, PersonSkill, ProjectSkillRequirement, Scenario, TeamAccessGrant, ProjectAccessGrant — gained a direct, `NOT NULL`, `FK ondelete=RESTRICT` `organization_id`, enforced at the repository layer by deliberately shadowing `BaseRepository`'s unscoped `get`/`list` signatures so an unconverted call site is a Pyright strict type error, not a silent cross-tenant leak. Role moved off `User` (a global login identity) onto a new `OrganizationMembership` (`user_id` + `organization_id` + `role`, reusing Phase 10's five-role vocabulary verbatim) — the same person can be Owner of one organization and Viewer of another. The active organization lives on the server-side `UserSession`, never trusted from a client-supplied id, and is re-verified against live membership/organization state on every single request, not just at login. Cross-organization access to an existing resource returns 404, matching Phase 11's precedent that an authorization boundary should never confirm a resource exists somewhere it shouldn't be visible. `ExportService`/`ImportService`/`InsightService`/`AIContextBuilder` — the four highest cross-tenant-leak-risk areas identified by audit — were hardened to thread `organization_id` through every query, closing several genuinely unscoped fallback paths (not just the ones that happened to be exercised by existing tests) in the process. See [docs/adr/0012-organizations-multi-tenancy.md](./adr/0012-organizations-multi-tenancy.md) for the full design, the audit findings, and the migration strategy.

Phase 13 adds risk management (`app/models/risk.py`, `app/domain/risk.py`, `app/services/risk.py`, `app/api/v1/projects.py`'s `/{project_id}/risks` routes, `apps/web/src/features/risks/`): a `Risk` record — description, cause, potential effect, probability, impact, response, owner, status, review date (CLAUDE.md §17's exact field list) — scoped to a `Project` and organization-scoped like every Phase 12 entity, following `ProjectSkillRequirement`'s exact CRUD/authorization shape (`require_project_access` for writes, global reads). `exposure` is never a stored column — it's derived at read time from `probability`×`impact` via an explicit lookup table in `app/domain/risk.py`, matching CLAUDE.md §17's "do not create risk scores that imply false precision." Two new signal types (`risk_high_exposure`, `risk_review_overdue`) plug into the **existing** Phase 5/7 Insights pipeline (`InsightService._project_signals`) with no new route, the same mechanism Phase 7 used for skill bottleneck signals. Phase 13's own audit before implementation confirmed CLAUDE.md's phase roadmap (§39) had never named a "Phase 13" — the amendment recorded there documents the resolution. See [docs/adr/0013-phase-13-risk-management.md](./adr/0013-phase-13-risk-management.md) for the full design.

Phase 14 adds stakeholder management (`app/models/stakeholder.py`, `app/services/stakeholder.py`, `app/api/v1/projects.py`'s `/{project_id}/stakeholders` routes, `apps/web/src/features/stakeholders/`): a `Stakeholder` record — name, an optional link to an existing `Person`, role, influence, interest, decision authority, communication needs (CLAUDE.md §16's field list) — following `Risk`'s exact CRUD/authorization/organization-scoping shape. Stakeholders are deliberately not forced into the internal `Person` model — `person_id` is optional and `SET NULL` on delete, since real stakeholders (clients, regulators, partner-organization executives) are frequently external to the org's own staffed roster. `influence`/`interest` are stored 3-tier enums (the established stakeholder power/interest grid's two axes) and `decision_authority` a 3-level enum; none are ever combined into a score or "engagement quadrant" — CLAUDE.md §16/§17's "no false precision" rule applies here exactly as it does to Risk. Deliberately **not** integrated into Insights (§16 defines no deterministic signal to surface — inventing one would be exactly the unrequested scoring/recommendation engine CLAUDE.md warns against) and **not** registered into Import/Export (not specified, deferred matching Phase 13's own precedent). See [docs/adr/0014-phase-14-stakeholder-management.md](./adr/0014-phase-14-stakeholder-management.md) for the full design.

Phase 15 adds the last-owner invariant (`app/repositories/{organization_membership,user}.py`'s `change_role_if_safe`/`revoke_if_safe`/`disable_if_safe`): every active Organization must retain at least one active Owner — one whose `OrganizationMembership` is active AND whose `User` account is active, since a disabled account cannot authenticate at all (`AuthService.login`/`resolve_session`). Three mutation paths are guarded — Owner→non-Owner role change, Owner membership revocation, and Owner account deactivation (the account-deactivation path was the literal Phase 12 gap ADR 0012 deferred; the other two already had a same-shape check, now hardened) — each via an atomically guarded `UPDATE` (the invariant folded into the write's own `WHERE` clause) rather than a separate read-then-decide-then-write, closing a genuine concurrent-request race verified against a real file-backed SQLite database. No schema change, no new permission, no frontend change (no membership- or user-management UI exists yet to guard). See [docs/adr/0015-last-owner-invariant.md](./adr/0015-last-owner-invariant.md) for the full design, including the concurrency mechanism and its documented limits.

Phase 16 completes the Phase 11 instance-authorization audit rather than extending its surface: every remaining documented gap (Team→Project inheritance, instance-level scoping for Person-keyed resources, Scenario instance-scoping) was re-examined against the current codebase and CLAUDE.md, and each was deliberately **retained** — no `PersonAccessGrant`, no `Project.team_id`, no `Scenario` ownership FK, since none is required by any existing specification and inventing one would be exactly the unrequested product semantics CLAUDE.md warns against. What Phase 16 *did* find and close was a test-coverage gap: only Risk and Stakeholder (Phases 13/14) had a dedicated cross-organization regression test; every other organization-owned entity (Person, Team, TeamMembership, Skill, PersonSkill, ProjectSkillRequirement, WorkingSchedule, AvailabilityException, Allocation, Scenario) did not, despite Phase 12 already enforcing the boundary in the repository layer. `tests/api/test_cross_organization_boundaries.py` and `tests/api/test_cross_resource_escalation.py` close that gap — twenty-six new tests total, all passing against unmodified production code, plus the missing Manager-grant IDOR block added to `test_risks.py` to match its sibling `test_stakeholders.py`. Import/Export, Insights, and AI-context boundaries were independently re-verified with one regression test each. 0 new tables, 0 migrations, 0 new permissions, 0 behavior changes. See [docs/adr/0016-instance-authorization-completion.md](./adr/0016-instance-authorization-completion.md) for the full authorization matrix and the reasoning behind each retained decision.

Phase 17 adds a v1 prioritization engine (`app/domain/prioritization.py`, `app/models/{prioritization_framework,prioritization_criterion,project_priority_score,project_priority_criterion_value}.py`, `app/api/v1/prioritization.py`, `apps/web/src/features/prioritization/`): CLAUDE.md §18's "what should this organization work on first?" question, answered by an organization-chosen framework rather than one CapacityOS prescribes. RICE and Weighted Scoring share one generic scoring engine (a framework's criteria + weights, dispatched by `framework_type` to a named formula — never an invented multiplier); a score's numeric result is never stored, always recomputed at read time from its recorded criterion inputs plus the framework's current definition, the same "derive, never cache" discipline `Risk.exposure` already established. An incomplete score reports exactly which criteria are missing rather than treating a gap as zero, and is ranked last, unranked, in the portfolio view. Framework management is deliberately Admin/Owner only (`Permission.PRIORITIZATION_MANAGE`) — stricter than Skill's Manager-writable catalog precedent, since a framework edit reshuffles the whole portfolio at once; scoring a specific project is Manager+, grant-scoped through the existing Phase 11 `ProjectAccessGrant` mechanism exactly like Risk/Stakeholder/Allocation. This is a deliberately reduced v1 slice, confirmed with the user before implementation (CLAUDE.md §31, "smallest complete slice"). See [docs/PRD-phase-17-prioritization.md](./PRD-phase-17-prioritization.md) for the original product design and [docs/adr/0017-prioritization-engine.md](./adr/0017-prioritization-engine.md) for what was actually built and why.

Phase 18 completes the framework set the Phase 17 PRD named (`app/domain/prioritization.py`'s `calculate_ice_score`/`calculate_wsjf_score`/`calculate_moscow_result`/`detects_cycle`, `app/models/project_dependency.py`, `apps/web/src/features/prioritization/components/{FrameworkCriteriaEditor,DependencyManager,DependencyGraphTable}.tsx`): ICE and WSJF reuse RICE's fixed-criteria seeding machinery (generalized, not duplicated, via `FIXED_CRITERION_KEYS`); MoSCoW is deliberately categorical, never coerced onto an invented numeric scale (CLAUDE.md §17's "no false precision," applied here exactly as it already is to Risk). A Weighted Scoring framework's criteria can now be added/renamed/reweighted/removed after creation, each edit independently re-checking `is_editable` server-side regardless of what the UI shows. `ProjectDependency` (blocks/related/enables) adds a directed project graph with cycle detection scoped to `blocks` edges only, surfaced as a table-based Dependency Graph view (no new charting dependency — CLAUDE.md §29 forbids decorative charts). No new permission was introduced — criteria edits reuse `PRIORITIZATION_MANAGE`, dependency create/delete reuse `PRIORITIZATION_SCORE` via the same Phase 11 `ProjectAccessGrant` mechanism. See [docs/adr/0018-prioritization-frameworks-and-dependencies.md](./adr/0018-prioritization-frameworks-and-dependencies.md) for what was actually built and why.

**Still not implemented**, by design: external integrations, SSO/OAuth, billing, organization hierarchies, Risk and Stakeholder Import/Export registration, org-wide cross-project risk/stakeholder registers, and a stakeholder engagement-quadrant classification. **Deliberately retained, not merely unbuilt** (Phase 16 audited and closed these as open questions — see [docs/adr/0016-instance-authorization-completion.md](./adr/0016-instance-authorization-completion.md)): Team→Project access inheritance and instance-level scoping for Person-keyed resources (WorkingSchedule, AvailabilityException, PersonSkill) or Scenario remain role-only, because no existing specification defines the ownership concept either would require. **Deferred to a later prioritization phase, not dropped** (Phases 17/18's own scoped boundary — see [docs/adr/0017-prioritization-engine.md](./adr/0017-prioritization-engine.md)'s and [docs/adr/0018-prioritization-frameworks-and-dependencies.md](./adr/0018-prioritization-frameworks-and-dependencies.md)'s Consequences): portfolio snapshots, scenario-vs-baseline ranking comparison, AI priority explanation, and Prioritization/`ProjectDependency` Import/Export registration. Phases 1–18 exist to give those later phases trustworthy source data, a trustworthy engine, a safe what-if layer, a decision-support layer, a data-portability boundary, a skill/capability dimension, a provider-agnostic interpretation layer, a production-ready operational foundation, an identity/authorization foundation — role-based and instance-scoped, now audited complete — a multi-tenant boundary underneath all of it, a risk dimension, a stakeholder dimension alongside skills, a guarantee that every organization keeps a working Owner, and now a decision-support layer connecting all of it to what to work on next, including how projects depend on each other. See [docs/adr/0001-phase-0-bootstrap.md](./adr/0001-phase-0-bootstrap.md) for the original bootstrap.
